# SSH Logger

여러 Linux 서버의 SSH 접속과 프로그램 실행 기록을 한곳에서 조회하는 셀프 호스팅 감사 대시보드입니다. Linux audit 로그를 Go 수집기로 전송하고, Go API와 SQLite에 저장한 뒤 React·TypeScript 웹 화면에서 조회합니다.

**현재 상태:** 초기 개발 버전입니다. 합성 감사 로그를 이용한 수집·API·브라우저 테스트를 제공하며, 실제 Ubuntu 호스트의 OpenSSH/PAM/auditd 조합에 대한 종단 간 검증은 아직 완료하지 않았습니다. 적용 전 [검증 범위와 배포 점검 항목](docs/validation.md)을 확인하세요.

## 주요 기능

- SSH 로그인 성공·인증 실패·세션 종료 기록과 현재 접속 상태 조회
- 실행 프로그램·인자·로그인 UID·실행 UID·PID·부모 PID 조회 및 세션 연결
- 활동 검색과 주요 활동·보조 실행 필터, 긴 스크립트 펼쳐 보기
- 서버별 수집 토큰 발급·재발급·폐기 및 수집 상태 확인
- 관리자 계정 생성, 자신의 비밀번호 변경 및 계정별 세션 만료
- SQLite 기반 로컬 전송 큐, 재전송과 중앙 중복 제거
- 알려진 민감 인자 마스킹, 보관 기간 설정, 일관성 있는 DB 백업·복원

셸 내장 명령과 터미널 출력은 기록하지 않습니다. 실행 성공은 프로그램의 최종 종료 코드가 아니라 `exec` 시스템 호출 결과입니다. 자세한 범위는 [수집의 정확한 의미](#수집의-정확한-의미)를 참고하세요.

## 구성

```text
대상 Linux 서버                         중앙 서버
OpenSSH / PAM → auditd → Go 수집기 ─HTTPS→ TLS 리버스 프록시
                         │                       │
                    SQLite 전송 큐          Go API → SQLite
                                                 ↑
                                          React 대시보드
```

중앙 서비스는 Docker Compose, 수집기는 대상 서버의 systemd 서비스로 실행합니다. 원격 수집에 사용하는 TLS 리버스 프록시는 별도로 구성합니다. 중앙 서비스는 SQLite를 사용하는 단일 인스턴스 구조입니다.

## 빠른 실행

저장소를 클론하고 프로젝트 루트에서 실행합니다.

```bash
git clone https://github.com/isac7722/ssh-logger.git
cd ssh-logger
```

필수 도구: Docker Engine, Docker Compose v2 이상(`--wait` 지원), GNU Make, Python 3. Go와 Node.js를 호스트에 설치할 필요는 없습니다.

```bash
make up
make status
```

브라우저에서 **http://localhost:8080** 을 엽니다. 관리자 계정은 `admin`이며, 최초 실행 시 생성된 비밀번호는 다음 명령으로 확인합니다.

```bash
cat .secrets/admin_password
```

`make up`은 `.env`와 초기 비밀번호 파일을 없을 때만 생성하고 이미지를 빌드한 뒤 상태 점검이 성공할 때까지 기다립니다. 첫 화면은 빈 상태이며, 서버를 연결하면 실제 기록이 표시됩니다. 예제 데이터는 자동으로 생성하지 않습니다.

최초 생성할 관리자 이름을 변경하려면 첫 `make up` 전에 `make init`을 실행하고 `.env`의 `ADMIN_USER`를 수정합니다. 이미 생성된 계정은 이 값만 수정해도 이름이 바뀌지 않으므로 DB의 계정 이름도 변경해야 합니다.

비밀번호는 최초 DB 생성 시 해시로 저장합니다. 이후 `.secrets/admin_password`만 수정해도 기존 관리자 비밀번호가 바뀌지는 않습니다. `.secrets` 디렉터리는 호스트 소유자만 접근 가능하고, 내부 파일은 비특권 컨테이너에서 읽을 수 있는 권한으로 생성합니다. 초기 비밀번호 파일과 백업은 Git에서 제외합니다.

다른 컴퓨터에서 접속하려면 우선 SSH 터널을 사용할 수 있습니다.

```bash
ssh -L 8080:127.0.0.1:8080 <사용자>@<대시보드-서버>
```

터널 연결 후 로컬 브라우저에서 같은 `http://localhost:8080`을 엽니다.

## 초기 관리자 ID/PW 설정

별도의 `superadmin` 등급은 없습니다. 최초 생성 계정과 추가 관리자는 같은 관리 권한을 갖습니다. 기본 ID는 `admin`이며, 비밀번호는 최초 설정 시 임의로 생성됩니다.

원하는 ID/PW를 사용하려면 **첫 `make up` 전에** 다음 순서로 설정하세요.

```bash
make init
```

1. `.env`의 `ADMIN_USER=admin`을 원하는 ID로 바꿉니다. 예: `ADMIN_USER=superadmin`.
2. `.secrets/admin_password` 파일 내용을 원하는 비밀번호 한 줄로 바꿉니다. 비밀번호는 UTF-8 기준 12–72바이트여야 하며 앞뒤 공백은 초기화 과정에서 제거됩니다.
3. `make up`을 실행하고 지정한 ID/PW로 로그인합니다.

이미 DB가 생성된 뒤에는 `.env`나 비밀번호 파일을 수정해도 기존 계정이 바뀌지 않습니다. **관리자 계정 → 내 비밀번호 변경**에서 현재 비밀번호와 새 비밀번호를 입력하세요. 변경 후 해당 계정의 모든 기기에서 로그아웃되며 새 비밀번호로 다시 로그인해야 합니다. 초기 비밀번호 파일은 변경된 비밀번호로 자동 갱신되지 않습니다.

**관리자 계정 → 관리자 계정 생성**에서 다른 관리자를 추가할 수 있습니다. 새 계정명은 영문·숫자로 시작하는 1–64자의 영문·숫자·점·밑줄·하이픈을 지원합니다. 추가 관리자도 모든 기록 조회, 서버·보관 설정 관리, 관리자 계정 생성 권한을 갖습니다. 다른 관리자의 비밀번호 재설정, 계정 삭제와 역할별 권한 분리는 현재 제공하지 않습니다.

## 관리 명령

저장소 루트에서 실행합니다.

| 명령 | 동작 |
| --- | --- |
| `make` / `make help` | 도움말 |
| `make up` | 초기 설정 생성, 이미지 빌드, 백그라운드 실행 및 상태 점검 |
| `make down` | 컨테이너·네트워크 종료 및 제거, 영구 볼륨 유지 |
| `make reload` | 이미지 재빌드·컨테이너 재생성, 잠시 서비스 중단 |
| `make status` | 중지된 컨테이너를 포함한 상태 확인 |
| `make logs` | 중앙 서비스 로그 확인, Ctrl+C로 조회 종료 |
| `make init` | 설정·초기 비밀번호 파일만 생성 |
| `make agent` | `bin/ssh-logger-agent` 빌드 (`AGENT_PLATFORM=linux/arm64`로 교차 빌드 가능) |
| `make test-deploy` | 일회용 컨테이너에서 CPU별 설치·업데이트 모의 검증 |
| `make test` | Go 테스트, TypeScript 검사 및 웹 빌드 |
| `make integration` | 18080 포트의 격리된 테스트 서비스에서 수집기·Chromium 검증 후 테스트 볼륨 삭제 |
| `make backup` | 실행 중인 SQLite의 일관성 있는 백업 생성 |
| `make restore BACKUP=backups/<파일>.db` | 현재 DB 백업 후 지정 백업으로 복원 |

기본 Compose 파일은 `compose.yaml`입니다. 다른 파일은 모든 명령에 동일하게 `COMPOSE_FILE=경로`를 지정하세요. 경로를 옮기면 Compose의 상대 경로(build, secrets)도 조정해야 합니다.

중앙 서비스 관리 명령은 원격 SSH 서버 수집기를 제어하지 않습니다. `status`는 컨테이너 상태이며 실제 수집 상태는 대시보드의 서버 관리 화면에서 확인합니다.

## 원격 수집을 위한 HTTPS

기본 바인딩은 `127.0.0.1:8080`입니다. 원격 수집기 연결 시 중앙 서버 앞에 신뢰할 수 있는 TLS 인증서를 사용하는 리버스 프록시를 설치하고 `.env`의 주소를 맞추세요.

```dotenv
PUBLIC_ORIGIN=https://logs.example.com
BIND_ADDRESS=127.0.0.1
PORT=8080
ADMIN_USER=admin
```

호스트의 프록시는 `127.0.0.1:8080`으로 전달하도록 구성하고 `make reload`를 실행합니다. 앱이 보는 `Origin` 헤더를 변경하지 마세요. HTTPS origin에서는 Secure 쿠키가 적용됩니다. URL의 호스트·포트가 `PUBLIC_ORIGIN`과 다르면 로그인 및 변경 요청이 거부됩니다. TLS 프록시와 도메인 발급은 배포 환경에 맞게 별도로 구성합니다.

## 서버 수집기 설치

설치 지원 대상은 **Ubuntu 24.04 LTS / x86_64 또는 ARM64 / OpenSSH + PAM + auditd**입니다. ARM64는 네이티브 64비트 실행을 수집하며 32비트 ARM 호환 실행은 지원하지 않습니다. 이 환경의 실서버 감사 커널 검증은 아직 필요합니다. 다른 배포판에서는 로그 형식·감사 규칙·서비스 이름을 확인해야 합니다.

### 한 줄 설치

먼저 대시보드의 **서버 관리 → 서버 등록**에서 수집 토큰을 발급합니다. 대상 Ubuntu 서버에서 `curl`과 sudo 권한(또는 root)이 필요합니다.

```bash
bash <(curl -fsSL https://raw.githubusercontent.com/isac7722/ssh-logger/main/install.sh)
```

설치 스크립트는 CPU를 자동 감지합니다(`x86_64` → `amd64`, `aarch64`·`arm64` → `arm64`). APT로 auditd·Go·curl·CA 인증서·tar를 설치하고, 소스를 다운로드해 수집기를 빌드합니다. Go 버전은 `go.mod`에 맞춰 자동 다운로드합니다. Docker나 수동 파일 복사는 필요하지 않습니다. 설치 중 중앙 서버의 HTTPS 주소와 토큰을 입력하세요. 시스템 패키지는 남고 임시 소스·Go 빌드 캐시는 종료 시 삭제합니다. GitHub, Ubuntu 패키지 저장소와 Go 모듈·도구 다운로드 경로에 접근할 수 있어야 합니다.

기존 수집기가 있으면 설정을 덮어쓰지 않고 중단합니다. 기존 설치는 [수집기 업데이트 절차](#활동-기록과-수집기-업데이트)를 사용하세요. 특정 버전을 설치하려면 아래 두 `main`을 동일한 태그 또는 커밋 SHA로 바꿉니다.

```bash
SSH_LOGGER_REF=main bash <(curl -fsSL https://raw.githubusercontent.com/isac7722/ssh-logger/main/install.sh)
```

### 수동 설치

1. 대시보드의 **서버 관리 → 서버 등록**에서 이름을 입력하고 발급 토큰을 보관합니다.
2. 중앙 프로젝트에서 `make agent`로 수집기를 빌드합니다. 대상 서버의 CPU가 다르면 아래 교차 빌드를 사용합니다.
3. 대상 서버에 `bin/ssh-logger-agent`와 `deploy/` 디렉터리를 같은 상위 디렉터리 구조로 복사합니다.
4. 대상 서버에 auditd를 설치하고 실행합니다.

```bash
sudo apt-get update
sudo apt-get install auditd
sudo systemctl enable --now auditd
sudo bash deploy/install-agent.sh
```

다른 CPU의 서버에 배포할 때는 대상 플랫폼을 지정해 빌드합니다. Go 빌드는 빌드 머신에서 실행하므로 ARM 에뮬레이터가 필요하지 않습니다.

```bash
# Intel/AMD 머신에서 ARM64 수집기 빌드
make agent AGENT_PLATFORM=linux/arm64
# x86_64 수집기 빌드
make agent AGENT_PLATFORM=linux/amd64
```

결과는 `bin/ssh-logger-agent`이며 마지막 빌드가 덮어씁니다. 둘 다 보관하려면 `AGENT_OUTPUT=bin/arm64`처럼 출력 경로를 지정하고 대상 서버에서는 선택한 바이너리를 `bin/ssh-logger-agent` 위치에 복사하세요. `deploy/` 디렉터리는 전체를 함께 복사합니다. 설치·업데이트는 바이너리의 `-platform` 출력과 대상 CPU가 일치하는지 먼저 확인합니다.

x86_64에는 `deploy/audit.rules`의 b64·b32 규칙, ARM64에는 `deploy/audit-arm64.rules`의 b64 규칙을 적용합니다. [Ubuntu auditctl 문서](https://manpages.ubuntu.com/manpages/noble/man8/auditctl.8.html)의 아키텍처별 시스템 호출 테이블을 사용합니다.

설치 스크립트는 HTTPS 중앙 주소와 토큰을 입력받습니다. 토큰은 터미널 입력 시 표시하지 않고 `/etc/ssh-logger/token`에 저장합니다. 수집기는 토큰 파일을 전송할 때마다 읽으므로 토큰 재발급 후 이 파일을 바꾸면 됩니다.

설치 시 `/etc/audit/rules.d/ssh-logger.rules`를 추가하고 `augenrules --load`를 실행합니다. 기존 규칙을 지우는 `-D`는 사용하지 않습니다. 같은 이름의 다른 파일이 있으면 중단하고 병합을 요청합니다. 감사 설정이 immutable(`auditctl -s`의 enabled=2)이면 재부팅 등 기존 서버 정책에 따른 적용이 필요합니다. OpenSSH의 PAM 감사 이벤트와 기존 audit 제외 규칙도 확인하세요.

```bash
sudo auditctl -s
sudo auditctl -l
sudo systemctl status ssh-logger-agent --no-pager
sudo journalctl -u ssh-logger-agent -n 100 --no-pager
```

수집기 실행에는 감사 로그 및 `/proc/*/sessionid` 읽기 권한이 필요하여 systemd에서 root로 실행합니다. 감사 규칙은 loginuid가 설정된 `execve`·`execveat`를 기록하므로 로컬 로그인 실행도 포함될 수 있습니다. SSH 세션에 연결되지 않는 실행은 **연결 불명**으로 표시합니다.

## 서버 폐기

**서버 관리 → 폐기**는 서버의 수집 토큰을 무효화하고 논리 삭제 상태로 표시합니다. 폐기된 서버는 서버 목록·선택 필터·활동 기록·접속 세션·대시보드 집계에서 숨깁니다. 기존에 폐기한 서버에도 적용됩니다.

서버와 감사 기록은 DB에서 즉시 삭제하지 않으며 기록에는 기존 보관 기간 정책이 적용됩니다. 폐기된 서버는 토큰 재발급으로 다시 활성화할 수 없습니다. 새로 등록하려면 기존 이름과 다른 이름을 사용하세요. 대상 호스트의 수집기 서비스는 자동으로 중지되지 않습니다.

## 수집의 정확한 의미

- 인증 실패는 SSH의 `USER_LOGIN` 실패와 PAM의 `USER_AUTH` 실패를 모두 보관합니다. 한 인증 시도가 두 감사 이벤트를 남길 수 있으므로 화면의 실패 수는 고유 로그인 시도 수가 아니라 실패 기록 수입니다.
- OpenSSH/PAM이 auditd에 기록한 `USER_AUTH`, `USER_LOGIN`, `USER_START`, `USER_END`와 `SYSCALL`·`EXECVE` 레코드를 조합합니다. journald/auth.log를 별도로 중복 수집하지 않습니다.
- 기본적으로 설치 시점의 audit.log 끝에서 시작합니다. 설치 이전 기록은 가져오지 않으며 이미 열려 있던 세션은 접속 시작 정보가 없을 수 있습니다. 설치 후 새 SSH 세션으로 확인하세요.
- 부팅 ID와 감사 세션 ID를 조합해 재부팅 후 세션 ID 재사용을 구분합니다. 세션 생성 근거가 없으면 임의 연결하지 않습니다.
- 현재 접속은 `/proc`의 sshd 프로세스 감사 세션과 최근 서버 보고를 함께 확인합니다. 60초 이상 보고가 없으면 과거 접속을 현재 접속으로 확정하지 않습니다.
- 셸 내장 명령, 리다이렉션 원문, 터미널 출력은 수집하지 않습니다. 실행 이벤트의 성공 여부는 exec 시스템 호출 결과이며 실행 프로그램의 종료 결과가 아닙니다.
- 알려진 비밀번호·토큰 인자는 로컬 큐 저장 전에 마스킹하고 서버에서도 재검사합니다. 임의 위치의 비밀값을 완벽히 제거할 수는 없습니다. 원본 시스템 audit.log의 정책은 서버 관리자가 관리합니다.
- 원래 로그인 UID와 실행 effective UID를 분리합니다. 공용 계정으로 접속한 개인을 확정 식별할 수 없습니다.

## 전송 장애·로그 회전

기본 로컬 큐는 `/var/lib/ssh-logger/spool.db`이며 최대 **64MiB의 이벤트 JSON**을 보관합니다. SQLite 인덱스·재사용 페이지·WAL 공간은 별도이므로 디스크 전체 사용량은 이보다 큽니다. `--buffer-mib`로 변경할 수 있습니다.

큐 포화 시 오래된 미전송 기록을 유지하고 새 기록을 버리며 카운터를 증가시킵니다. 이벤트 JSON 256KiB 초과나 지원 필드 길이 초과도 같은 방식으로 처리합니다. 중앙 커밋 성공(HTTP 200) 후에만 로컬 큐에서 제거합니다. 성공 응답이 유실되면 재전송하고 중앙 고유 키로 중복을 제거합니다. 정상 전송은 최대 5초 간격이며 상태 보고도 함께 보냅니다. 장애 시 재시도는 최대 60초까지 늘어납니다.

읽기 위치와 이벤트 큐를 같은 트랜잭션으로 저장합니다. 이름 변경 방식 로그 회전에서는 inode로 이전 파일을 찾아 읽은 뒤 새 파일로 이동합니다. 이전 파일이 이미 삭제·압축되었거나 copytruncate로 읽지 못한 부분이 사라지면 완전 복구할 수 없습니다. 재부팅 시 읽지 못한 이전 부팅 로그도 자동 재해석하지 않습니다. 이러한 경우 카운터를 증가시킵니다. **카운터는 알려진 이벤트 손실 수와 크기를 알 수 없는 공백 발생 횟수의 합이며 정확한 총 손실 이벤트 수가 아닙니다.** 공백이 발생한 수집기는 경고 상태를 유지합니다.

서버 시계는 NTP로 동기화하세요. 1MiB를 넘는 원본 로그 행, 손상된 로그, 중앙보다 5분 이상 미래인 시각은 정상 수집을 방해할 수 있으며 서비스 로그에서 확인해야 합니다.

## 백업·복원과 공간 관리

```bash
make backup
make restore BACKUP=backups/sshlogger-<시각>.db
```

백업은 `VACUUM INTO`를 사용하며 실행 중 DB 파일만 복사하지 않습니다. `backups/`의 파일을 외부 저장소에 따로 보관하세요. 백업에는 관리자 해시, 서버 인증 토큰 해시, 세션과 설정이 포함됩니다.

복원은 무결성·스키마 확인 → 현재 DB 자동 백업 → 서비스 중지 → DB 교체 → 서비스 시작 순서입니다. **현재 데이터를 지정 시점의 데이터로 교체하며 백업 이후 기록·계정 변경은 되돌아갑니다.** 실패하면 자동 재시작하지 않고 오류를 표시합니다. 정상 서비스가 없어 사전 백업할 수 없는 재해 복구는 별도 절차가 필요합니다. 실행 중인 DB를 직접 덮어쓰지 마세요.

오래된 기록은 매분 최대 1,000개씩 삭제하므로 보관 기간을 크게 줄이면 정리 시간이 필요합니다. SQLite는 삭제된 페이지를 재사용하며 DB 파일이 즉시 작아지지 않습니다. 디스크 반환이 필요하면 백업한 뒤 해당 백업을 복원하면 압축된 스냅샷으로 교체됩니다. 중앙 WAL은 매분 passive checkpoint, 수집기 WAL은 주기적으로 truncate checkpoint를 수행합니다.

## 활동 기록과 수집기 업데이트

활동 목록과 세션 상세는 기본적으로 **주요 활동**을 표시합니다. **전체 기록** 또는 **보조 실행**으로 전환하면 제외된 항목과 분류 사유를 확인할 수 있습니다. 환경 조회·문자열 처리의 알려진 프로그램과 정확한 인자 조합만 분류하며, 실패·결과 불명·로그인 계정과 실행 계정이 다른 실행은 주요 활동에 남깁니다. 기록을 삭제하지 않으며 기존 기록에도 적용됩니다. 긴 스크립트는 펼쳐서 볼 수 있습니다.

주요 활동은 직접 입력 명령만을 의미하지 않습니다. 같은 보조 명령을 직접 입력해도 분류될 수 있습니다. 후속 개선 계획은 [활동 기록 개선안](docs/activity-improvements.md)을 참고하세요.

새 수집기는 감사 로그의 PID·부모 PID를 저장합니다. 기존 기록은 **미수집**으로 남고 부모 프로그램명은 아직 표시하지 않습니다. 중앙 서버를 먼저 업데이트한 뒤, 수집기가 설치된 각 서버에서 다음을 실행하세요.

```bash
make agent
sudo bash deploy/update-agent.sh
```

업데이트 스크립트는 기존 토큰·설정·감사 규칙·전송 큐를 유지하고 바이너리만 교체한 뒤 서비스를 재시작합니다. 시작 실패 시 이전 바이너리를 복원합니다. 다른 서버에서 빌드했다면 대상 아키텍처에 맞는 `bin/ssh-logger-agent`와 스크립트를 같은 디렉터리 구조로 전달하세요. 기존 수집기도 새 중앙 서버에 계속 전송할 수 있지만 PID 필드를 제공하지 않습니다.

DB 스키마는 시작 시 버전 3으로 자동 이전합니다. 기존 계정과 감사 기록은 유지되며, 버전 1의 기존 이벤트 PID 필드는 NULL입니다. 버전 1·2의 로그인 세션은 소유 계정을 식별할 수 없어 폐기하므로 업데이트 후 다시 로그인해야 합니다. 업데이트 전 `make backup`을 실행하세요. 현재 복원 도구는 버전 1·2·3 백업을 지원하고 이전 버전은 시작 시 이전합니다.

## 개발과 검증

- [개발 스펙](docs/development-spec.md)
- [API 계약](docs/api.md)
- [검증 결과와 실서버 점검 항목](docs/validation.md)

Go 의존성은 `go.mod`·`go.sum`, 웹 의존성은 `package-lock.json`으로 고정합니다. 테스트와 빌드는 Docker 안에서 수행합니다. 이 저장소는 중앙 서비스 단일 인스턴스를 전제로 하며 SQLite 파일을 NFS 등으로 공유하지 않습니다.

`make integration`은 Linux의 host networking과 18080 포트를 사용하고 Playwright 컨테이너를 다운로드합니다. 테스트 데이터는 `ssh-logger-test` 프로젝트 전용이며 종료 시 해당 테스트 볼륨을 삭제합니다. 운영 데이터 볼륨은 사용하지 않습니다.


### 소스 구조

| 경로 | 역할 |
| --- | --- |
| `agent/` | audit 로그 파서, 체크포인트, 전송 큐 및 수집기 실행 |
| `server/` | 인증, 수집·조회 API, SQLite 저장과 스키마 이전 |
| `internal/model/` | 공통 이벤트 모델과 마스킹 |
| `web/` | React·TypeScript 대시보드 |
| `deploy/` | systemd 서비스, 감사 규칙, 설치·업데이트 스크립트 |
| `scripts/` | 초기 설정, 백업·복원, 통합 검증 도구 |
| `tests/` | 격리된 Compose 환경과 Playwright 테스트 |
| `docs/` | 개발 스펙, API 계약, 검증 범위 및 개선안 |

```bash
make test          # Go 테스트, TypeScript 검사, 웹 프로덕션 빌드
make integration   # 합성 audit 로그 수집 및 Chromium 화면 검증
```

Docker 빌드 환경은 Go 1.26과 Node.js 24를 사용합니다. 웹 의존성을 변경할 때는 `web/package-lock.json`도 함께 갱신하세요.

## 기여 및 문제 보고

버그 보고에는 재현 절차, 예상 동작과 실제 동작, 운영체제·CPU 아키텍처, 사용한 커밋과 관련 로그를 포함해 주세요. 수집 문제는 OpenSSH·PAM·auditd 설정 및 로그 회전 방식도 함께 알려주면 재현에 도움이 됩니다.

공개 이슈나 PR에 실제 토큰, 비밀번호, `.env`, `.secrets/`, DB·백업, 원본 감사 로그를 첨부하지 마세요. 감사 로그의 계정명·IP·명령 인자도 가상 값으로 바꾼 최소 재현 예시를 사용하세요.

변경을 제안할 때는 관련 문서와 필요한 테스트를 함께 갱신하고 `make test`를 실행해 주세요. 수집·API·화면 흐름을 변경했다면 `make integration`도 실행하고 결과를 남겨 주세요.
